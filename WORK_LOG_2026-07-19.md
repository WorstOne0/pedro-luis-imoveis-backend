## 1. Query builder moved and rewritten

`src/features/real_estate/controllers/real_estate_query.js` → **deleted**
`src/features/real_estate/utils/real_estate_query.js` → **new**

A query builder is not a controller. Behaviour changes:

- **No default limit.** The public map needs every match to draw its markers, so
  paging would actively break it. `limit` stays available for callers that want a
  slice.
- `minArea` / `maxArea` range support.
- `exclude` param — used by "imóveis similares" so a listing doesn't appear among
  its own suggestions.
- User input is regex-escaped before being used in `$regex` (`escapeRegex`).
- Room/bathroom/garage counts are **"at least N"**, not exact.

## 2. District filtering — the one to know about

```js
// Before
if (query.district) filter["address.district"] = String(query.district);
```

Two problems: single value only, and **exact match**.

The public map's polygon names are uppercase (`CANCELLI`) while the listings are
title case (`Cancelli`). Measured against the real data: **exact-case matches
were 0**. Clicking any district on the map would have returned an empty list, no
matter how well the frontend behaved.

Now: comma-separated, matched case-insensitively via anchored regex, `$in` for
several. `city` got the same treatment.

Verified against live data:

```
CENTRO                            → 9
centro                            → 9
Centro,Cancelli                   → 11
CENTRO,CANCELLI                   → 11
Centro,Cancelli,Recanto Tropical  → 15
```

**Still accent-sensitive** — `district=CANADA` returns 0 against stored `Canadá`.
The frontend compensates by resolving polygon names to the catalogue's spelling
before calling the API, so that step is load-bearing. If you want the API robust
on its own, fold accents here too.

## 3. `stats` endpoint deleted

`GET /real_estate/stats` (62-line controller + route) is gone. It ran
`RealEstate.find({}, {price: 1})` — a full collection scan — on every call, to
produce price-histogram buckets the client already had the data for. The
frontend now computes them from the catalogue it already fetches.

## 4. Controller — `src/features/real_estate/controllers/real_estate_controller.js`

- **`WRITABLE` whitelist.** Anything else in the body is dropped, so a caller
  can't reach schema fields never meant to be exposed.
- `parseBody` merges the multipart `metadata` JSON string with the upload
  middleware's resulting urls.
- **Real HTTP status codes.** Responses used to return HTTP 200 with
  `{status: 500}` in the body, which meant the dashboard's
  `response.status !== 200` check never fired — logins appeared to succeed
  silently. Every response now carries a matching status.
- `runValidators: true` on `findOneAndUpdate`.
- `importOldDB` is gated behind `ENABLE_LEGACY_IMPORT !== "true"` → 404, plus
  `requireRole("super_admin")`.

## 7. Data problem — needs your attention

**17 of the 25 listings have `address.position = {lat: 0, lng: 0}`.** The legacy
importer wrote zeros where the old records had no coordinates, rather than
leaving them unset. Consequence: those listings plotted in the Atlantic off
Africa, and a plain `if (!position)` guard never caught them.

The frontend now filters them out, so **the public map shows 8 of 25 listings**.

Two fixes worth making here:

1. Backfill the coordinates — geocode the stored addresses, or surface the
   listings in the dashboard so they get set on edit.
2. **Change `importOldDB` to leave `position` unset** when the source has no
   lat/lng, so this can't recur on the next import.

## 8. Security fixes (earlier in the session, same working tree)

- **Path traversal in image delete** — `fs.rmSync("public/" + filename)` allowed
  `../../.env`. Fixed with `basename` plus a resolved-path check. See the
  `_images` log.
- `split("\\")` on upload paths was Windows-only and would return the full path
  on Linux/Docker → `path.basename`.
